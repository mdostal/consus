# Diagram editing library — cost/benefit analysis

*A `dostal:decision-request/v1`-shaped document (see `server/decision-contract/parser.ts`), rendered as readable markdown rather than the fenced JSON payload.*

## Context

Consus renders two Mermaid diagrams today, both read-only: the epic/story dependency cascade (`web/src/features/projects/DiagramView.tsx`, `buildMermaidSource()` → `graph LR` text, rendered via a dynamic `import("mermaid")`) and a per-repo architecture diagram (`web/src/features/projects/ArchitectureDiagramView.tsx`, `GET /api/diagrams/:repo/architecture` → `{ topLevel, fullComponent }` `graph TD` strings). `mermaid` (`^11.16.1`) is the only diagramming dependency in `package.json` — confirmed by reading it directly; the only other runtime deps are `better-sqlite3`, `fastify`, `js-yaml`, `marked`, `react`/`react-dom`.

Both existing views already share one propose-a-change mechanism: a "Propose a change" toggle opens a plain `<textarea>` diff plus a description input, and `onProposeChange({diff, description})` fires `POST /api/proposals`, which is generic — `server/routes/proposals.ts` requires only `{itemId, targetType, diff, description, requestedBy}` and has zero diagram-specific knowledge server-side. Whatever diagram-editing approach is chosen must produce something that collapses into that same `diff: string` field without inventing a parallel dispatch path.

Bundle size is not hypothetical: running `npm run build:web` today already emits `(!) Some chunks are larger than 500 kB after minification`, including `mermaid.core-*.js` at 635.60 kB raw / 152.13 kB gzip, `cytoscape.esm-*.js` at 443.80 kB raw / 142.40 kB gzip (Mermaid's own transitive dependency, used internally for its `architecture`/`mindmap` diagram types — not a first-class API Consus code calls), and `cynefin-*.js` at 690.56 kB raw / 155.09 kB gzip. These are lazy-loaded per diagram type (Mermaid code-splits itself), so they aren't paid for on every page load today, but they set the baseline for what "large" means in this app.

The operator need is real editing: move/add/remove nodes, edit labels, edit connections — for both a dependency **tree** (epics/stories/dependsOn) and a directory **graph** (architecture scan), each producing a diffable change through the existing proposal flow.

## Options

### A — Text-only editing of the existing Mermaid source

Add a code-editor-style `<textarea>` (or a lightweight syntax-highlighted box) that edits the `graph TD`/`graph LR` string directly, re-renders it live via the same `mermaid.render()` call already used, and diffs the before/after text as plain text for `POST /api/proposals`. Zero new dependencies, zero new bundle weight, and it reuses 100% of the existing render pipeline in both `DiagramView.tsx` and `ArchitectureDiagramView.tsx` (`buildMermaidSource`, `renderMermaid`, the timeout race, the sanitize/escape helpers) unchanged.

The real limitation is conceptual, not implementation cost: Mermaid `graph` syntax has no explicit node coordinates — layout is automatic via its own layout engine. So "move a node" isn't a representable edit in this format at all; the only expressible edits are structural (add/remove/rename nodes, add/remove/relabel edges), which does cover most of the stated ask (add/remove nodes, edit labels/connections) but not the "move" part literally. Editing raw graph syntax by hand is also unforgiving for non-technical operators — a typo breaks the whole render, and mapping a text edit back to "which story/epic did this change" for click-to-detail (`buildNodeLookup`/`findNodeKey` in `DiagramView.tsx`) requires re-parsing Mermaid text, which today only exists in the write direction (data → text), not read (text → data). This is the cheapest and lowest-risk option but the shallowest on the actual "editor" ask.

### B — React Flow (`@xyflow/react`)

The current package name is confirmed as `@xyflow/react`; the old `reactflow` name was rebranded starting with React Flow 12 (released July 2024) as the xyflow project unified its packages under one scope — `reactflow` (currently `11.11.4` on the npm registry) is not marked `deprecated` in registry metadata but is functionally superseded and no longer where new development happens. `@xyflow/react` is MIT-licensed, currently `12.11.3`, peer-deps on `react`/`react-dom` `>=17` (React 18 compatible, no upper bound). Per Bundlephobia: 187 kB minified / 59.8 kB gzip — smaller than either of the two Mermaid chunks already shipped today (mermaid.core at 152 kB gzip, cytoscape.esm at 142 kB gzip). The `xyflow/xyflow` monorepo has ~37.7k GitHub stars and is actively maintained (blog posts through 2025 on v12 and beyond).

React Flow's data model is exactly `{nodes: [...], edges: [...]}` — this maps cleanly onto both diagram shapes without contortion: the epic/story cascade is nodes (epics as parent/group nodes, stories as children) plus dependency edges; the directory-structure graph is nodes (folders/files) plus containment/reference edges. Both are already graphs today (that's what the Mermaid `graph` syntax encodes), so this is a like-for-like representation change, not a shape change. Because state is a plain JSON object, producing a diff for the existing `diff: string` field is a matter of serializing before/after JSON (or a derived structural summary) and either running a text-diff over the JSON or writing a small structured-diff formatter — non-trivial but well-scoped engineering, reusing patterns already proven in this codebase (e.g., the sectional diff work referenced from consus-phase12). React Flow also natively supports drag-to-move, which is the one edit type Option A structurally cannot express. The cost is real integration work: a new node/edge model needs bidirectional mapping to/from the existing `DiagramEpic[]`/`{topLevel, fullComponent}` API shapes, and a second rendering path alongside (or replacing) the Mermaid one — two diagram-shaped state representations to keep in sync if Mermaid view mode is kept for read-only display.

### C — Excalidraw (`@excalidraw/excalidraw`)

MIT-licensed, currently `0.18.1`, peer-deps `react`/`react-dom` `^17.0.2 || ^18.2.0 || ^19.0.0` (explicit React 18 support). Per Bundlephobia: 1.13 MB minified / 356 kB gzip — over 2x mermaid.core's gzip size and over 5x React Flow's, driven substantially by bundled font data and its full freeform-drawing engine (shapes, freehand, embedded fonts for text/SVG export). As of 2025 the package moved to an ESM/tree-shakable bundle format and made font embedding optional (`skipInliningFonts`), but the core scene-graph and rendering engine is still a much larger payload than a node/edge library. The project itself is far more mature/popular by star count (123k+ GitHub stars as of May 2026 vs. xyflow's ~37.7k) — but that popularity is for its actual product (a freeform whiteboard), not evidence it fits Consus's structured-graph use case.

The deeper mismatch is representational: Excalidraw's native state is a scene of freely-positioned, freely-shaped drawing elements (rectangles, arrows, freehand strokes, text) with no inherent semantic graph structure — no built-in concept of "this shape is story `s3`" or "this arrow is a `dependsOn` edge." Every node/edge semantic (id↔entity mapping, edge direction/meaning, click-to-detail wiring like `DiagramView.tsx`'s `buildNodeLookup`) would have to be built and maintained entirely in Consus's own code on top of Excalidraw's generic scene elements, and diffing that scene state into something meaningful for a story/epic-shaped or directory-shaped underlying data model is a much harder, lossier mapping than React Flow's already-graph-shaped API. Excalidraw is the right tool for freeform sketching/whiteboarding, not for editing two specifically graph-structured diagrams that already have real underlying entities.

### D — tldraw

Ruled out primarily on licensing, not technical fit. tldraw's SDK is source-available under its own license (`LICENSE.md`, not MIT) — production use requires a license key, and the free/hobby tier renders a permanent "Made with tldraw" watermark on the canvas; removing it requires a paid commercial license, and the SDK is documented to refuse to run in production (HTTPS, non-localhost, `NODE_ENV=production`) without a valid key. This conflicts with Consus's current all-MIT, no-commercial-dependency posture (`mermaid`, and every other listed runtime dep, is permissively licensed) and would put a paid-license gate in front of a feature in what is otherwise a free local tool. Not evaluated further on bundle size/API fit given this is disqualifying on its own.

### E — Commercial diagram SDKs (GoJS, JointJS+/Rappid)

Included for completeness since both are real, purpose-built node/edge diagramming SDKs with more built-in diagram affordances than React Flow (e.g., GoJS ships tree/org-chart layouts out of the box). Both are ruled out for the same reason: cost. GoJS (Northwoods Software) requires a paid per-developer license for any non-evaluation use (an individual/sole-proprietor license runs $3,995 perpetual+1yr support); its free/evaluation distribution renders a watermark. JointJS's core library is MPL-2.0 and free, but the plugin set needed for a real interactive node editor (advanced UI components, more layouts) sits in JointJS+ (the commercial product that replaced the Rappid brand as of a March 2026 rename), which is a paid subscription. Neither is a fit for a project whose entire dependency list today is free/permissive.

## Recommendation

**Recommended: B — React Flow (`@xyflow/react`).**

It is the only candidate whose native state (`{nodes, edges}`) is already the same shape as both diagrams Consus renders today — a tree is a graph, a directory structure is a graph — so it doesn't force either diagram into a foreign representation (Excalidraw's freeform scene) or fail to express real edits (Option A's positionless Mermaid text). It's MIT-licensed like everything else in this project, confirmed React 18-compatible, and at 59.8 kB gzip (Bundlephobia) it is smaller than either of the two Mermaid-internal chunks (`mermaid.core` at 152 kB gzip, `cytoscape.esm` at 142 kB gzip) the build already ships today — so while it is a new dependency, it is not the thing that would newly trip the existing >500 kB chunk warning. Its JSON node/edge state is also the most tractable of the candidates to turn into a real diff for the existing generic `POST /api/proposals` mechanism, since no semantic reconstruction (Option C) or hand-parsing of a positionless text format (Option A) is required first.

**Strongest counter-argument found during research:** bundle size is not the only cost, and by that measure Option A (zero new dependencies, zero new integration surface) is strictly cheaper and lower-risk. Adopting React Flow means building and maintaining a second diagram representation — a real bidirectional mapping between the existing `DiagramEpic[]`/`{topLevel, fullComponent}` API shapes and React Flow's `{nodes, edges}` model, plus a structured-diff formatter that turns a before/after node/edge state into something meaningful inside a single `diff: string` field, plus (if Mermaid's read-only rendering is kept for non-editing views) two independent diagram engines to keep visually consistent. That integration and diff-design work is a real, non-trivial engineering cost that a pure text-box approach avoids entirely, and it's the strongest reason a team optimizing for minimum implementation risk might choose A over B even knowing A can't express node movement.
