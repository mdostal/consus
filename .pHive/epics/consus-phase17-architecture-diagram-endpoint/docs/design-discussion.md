# Design Discussion: consus-phase17-architecture-diagram-endpoint

## Goal

`GET /api/diagrams` (`server/routes/diagrams.ts`) today serves exactly one kind of diagram: the
epic/story dependency cascade, built entirely from `.pHive/epics/*/epic.yaml` planning YAML
(`registerDiagramRoutes`, `server/routes/diagrams.ts:77-116` — the full contents of that file). It
says nothing about a repo's actual code. This epic adds a second, genuinely different diagram type —
a real per-repo architecture diagram derived from the repo's actual directory/file structure — so an
operator can see a repo's real shape, not just its planning artifacts. Standalone-only, local-only,
small-to-medium scope: one new read-only GET endpoint plus a directory-scanning generator. The
existing cascade endpoint is not modified.

## Current-state findings

- `server/routes/diagrams.ts:77-116` is the entire diagrams route file today: one handler,
  `GET /api/diagrams?repo=`, upserting a synthetic `items` row (`diagramItemIdFor`, lines 16-18) and
  returning `{ repo, itemId, epics }` from `.pHive/epics/*/epic.yaml`. `repos: Record<string, string>`
  (line 10) is the repo-name -> absolute-path map, identical shape to what `docs.ts`/`projects.ts` use.
- `server/index.ts:42` wires `registerDiagramRoutes(app, { db, repos })`; `repos` comes from
  `loadProjectRegistry` (`server/config/project-registry.ts:11-36`), which reads a JSON
  name->absolute-path map from `.pHive/consus-projects.json` (falling back to `{ consus: cwd }`),
  skipping any path that doesn't `existsSync`. So every registered repo path is already
  filesystem-verified to exist by the time it reaches a route handler.
- `server/db/migrate.ts` (full file read) has **no `diagrams` cache table** on mainline today —
  confirmed, every `CREATE TABLE` there is `items`, `audit_log`, `doc_index`, `kb_entries`,
  `kb_versions`, `comments`, `triage_overrides`, `artifact_links`, `proposals`, `events`. Nothing
  diagram-cache-shaped exists to build on.
- Archived precedent `archive/dev-2026-08-11-pantheon-coupled` commit `d01e078` added
  `GET /api/diagrams/:repo` returning `{ topLevel, fullComponent }`, generated by
  `server/lib/diagram-generator.ts` (`generateDiagrams`): a top-level dir scan (depth 1, `graph TD`)
  plus a depth-2 `fullComponent` walk, both capped at `MAX_COMPONENTS = 50`, with an `IGNORED_DIRS` set
  (`node_modules`, `dist`, `dist-server`, `build`, `coverage`, `.git`, `.pHive`, `.vite`, `.turbo`) and
  dotfile dirs skipped. It also folded in file-path-shaped mentions pulled from backtick code spans in
  `.pHive/epics/*/docs/design-discussion.md` via a regex (`extractComponentMentions`), tolerating
  missing/malformed docs without throwing. Results were cached in a `diagrams` table added alongside a
  Multica-backed cascade at PAN-7948/7955 — that cache existed mainly to avoid re-querying a slow
  external issue tracker for the *cascade*, not because the fs-scan generator itself was slow. This
  logic is pure local fs I/O — no coupling to any external system — so it ports cleanly as design
  precedent.
- Frontend: `web/src/features/projects/DiagramView.tsx` renders the cascade. It is tightly coupled to
  the `DiagramEpic[]`/`DiagramStory[]` shape end to end: `buildMermaidSource` builds `graph LR` text
  from epics/stories/dependsOn, `buildNodeLookup`/`findNodeKey` map rendered SVG node ids back to a
  specific story or epic for click-to-detail, and the component owns propose-a-change UI wired to
  `POST /api/proposals`. None of that fits a raw two-graph Mermaid response with no story/epic
  identities to look up. It is invoked from `web/src/App.tsx:420-482` (`ProjectDiagram`), itself called
  from `ProjectsSection` (`App.tsx:405`). `mermaid` (`^11.16.1`) is already a root `package.json`
  dependency (line 23) used by `DiagramView.tsx` via a dynamic `import("mermaid")` — no new frontend
  dependency is needed here either.

## Proposed approach

### New endpoint

`GET /api/diagrams/:repo/architecture` (kept as a distinct path segment, not a query param on
`/api/diagrams`, so there's zero ambiguity with the existing cascade route and no risk of Fastify route
overlap). 404s with the exact same shape the cascade endpoint already uses —
`{ error: "unknown repo: ${repo}" }` — for a repo not present in `repos`. On success, returns
`{ repo, topLevel, fullComponent }`, each a Mermaid `graph TD` source string.

### Generator (`server/lib/diagram-generator.ts`, new file)

`generateArchitectureDiagrams(repoPath: string): { topLevel: string; fullComponent: string }`, ported
from the archived precedent with no material algorithm changes (it was already standalone/local-only):

- **Component = a directory.** `topLevel` lists immediate subdirectories of the repo root as nodes off
  a `root` node (depth 1). `fullComponent` walks two levels deep, adding a node + edge from its parent
  for each subdirectory, skipping `IGNORED_DIRS` (build/vendor/vcs/tooling noise) and dotfile dirs.
- **Cap:** both graphs stop adding nodes once total node count reaches `MAX_COMPONENTS = 50`, so a huge
  monorepo can't produce an unusably large diagram.
- **Design-doc mentions:** `fullComponent` additionally scans every
  `.pHive/epics/*/docs/design-discussion.md` under the target repo for backtick-quoted, path-shaped
  spans (e.g. `` `server/adapters/foo.ts` ``) and adds each as its own node off `root`, up to the same
  cap. This is kept — it's genuinely useful (surfaces files the planning docs call out that a bare dir
  walk wouldn't show) and is pure local file reads with a try/catch per doc, so a malformed doc is
  skipped with a console warning rather than 500ing the whole request.
- IDs are sanitized (`[^a-zA-Z0-9_]` -> `_`) and labels have `"` escaped, matching the precedent, so
  arbitrary directory/file names can't break Mermaid syntax.

### Cache table: not adding one — on-demand generation only

The precedent's `diagrams` cache table existed to avoid re-hitting a slow external issue tracker for
the *cascade* diagram. The architecture generator has no such dependency: it's a bounded local
directory walk (depth-2, capped at 50 nodes) plus reading a handful of small local Markdown files —
on a modern machine this is low-single-digit-milliseconds even for a large repo, because the walk
itself is capped, not the whole tree. This repo's actual deployment is a handful of local,
single-operator repos with no concurrent-request load. Adding a cache table means a new migration,
invalidation reasoning (when does a stale cached diagram get refreshed as the repo changes on disk?),
and more surface area for a benefit that doesn't materialize at this scale. **Decision: generate on
every request, no cache table.** If this repo's scale assumptions change (many repos, much larger
trees, or a hosted multi-operator deployment), revisit — the precedent's `diagrams` table shape is
still available as a reference if that day comes.

### Frontend: new small view, `DiagramView.tsx` untouched

`DiagramView.tsx` is structurally built around `DiagramEpic[]`/`DiagramStory[]` (node-lookup-by-id,
click-to-detail, propose-a-change) — none of which exists for a raw two-graph architecture response.
Bending it to accept either shape would mean threading optional/union props through the click-handling
and detail-panel logic for a case that shares only "call `mermaid.render()` on a `graph TD` string."
**Decision: a small new component**, `web/src/features/projects/ArchitectureDiagramView.tsx`, taking
`{ repo, topLevel, fullComponent }` and rendering both graphs (e.g. tabbed or stacked, styling detail
left to implementation) using the same dynamic-`import("mermaid")` + render-with-timeout pattern
`DiagramView.tsx` already uses. The render-timeout logic (~15 lines) is deliberately duplicated rather
than extracted into a shared helper: extracting it would mean touching `DiagramView.tsx` and its test
file for a second, independent feature, which raises regression risk on the cascade view for no
functional benefit at this scope. Wired into `App.tsx`'s `ProjectsSection` as a new
`ProjectArchitectureDiagram` fetch-and-render component sitting alongside the existing
`ProjectDiagram`/`ProjectDocs` (`App.tsx:405-406`), not replacing either.

## Risks

- **Low — cap edge case.** A repo with exactly 50-plus directories at depth 1/2 could produce a
  `fullComponent` graph that omits some real directories once the cap is hit mid-walk (order is
  alphabetical via `listDirs`' sort, so it's deterministic, just not "most important first"). Accepted:
  same tradeoff the precedent made; documented in the generator's cap constant.
- **Low — design-doc mention regex is heuristic.** `extractComponentMentions`'s path-shaped regex can
  false-positive on a backtick span that merely looks path-like (e.g. `a/b` in prose) or miss a real
  path not backtick-quoted. Accepted as best-effort enrichment, not a source of truth — the directory
  walk is the primary signal.
- **Low — on-demand generation re-walks the fs on every request.** No caching means a slow disk (e.g.
  network-mounted repo path) pays the walk cost every fetch. Mitigated by the depth-2/50-node cap
  bounding the work regardless of true repo size; acceptable given local-only, single-operator scale
  (see cache-table decision above).

## Open questions (resolved)

- *Should the new route replace/merge into `/api/diagrams`?* No — kept as a fully separate path
  (`/api/diagrams/:repo/architecture`) so the existing cascade endpoint's query-param contract and
  tests are untouched, per this epic's explicit scope constraint.
- *Tabbed vs. stacked rendering of `topLevel`/`fullComponent` in the UI?* Left to implementation
  discretion in the story — either satisfies the acceptance criteria (both graphs visibly rendered);
  not a decision worth blocking planning on.
